# Public Casey beta

Entry: `/prova.html`. Native College/Campus public chat also uses this individually metered backend. The staff kiosk and authenticated College backend remain separate.

## Identity and privileges

A guest receives 256+ bits of random bearer capability, persisted on its browser. Only its SHA-256 digest is stored in `casey_beta_visitors`. This guest identity is separate from Supabase Auth's `authenticated` database role; no anonymous Auth setting or existing RLS policies are broadened. Beta tables have RLS and no anon/authenticated grants. The service-only, security-invoker RPC authenticates capabilities and atomically manages ownership, quotas and leases.

After proof of email ownership through Supabase Auth, the server links the guest history to the verified `auth.users` identity. Access to a linked capability additionally requires the matching verified JWT. Other devices can list and restore only conversations linked to that identity. No student role, roster record, private academic record or booking permission is created. College bookings retain the pre-existing identity and explicit confirmation requirements.

Auth challenges are generated by Supabase, delivered through Casey's existing Gmail OAuth sender (existing gmail.send grant, encrypted refresh credential). There are no shared passwords, new email provider subscriptions, browser service keys, exposed OTPs, exposed links or logged mail bodies. Challenges are sent only after a visitor explicitly requests email access. The beta sender enforces one email per address per minute, 50 per IP/hour and 100 globally/24h. URL allowlist must include the production `/prova.html` route. The existing production wildcard includes it.

## Limits and operations

- Per guest/verified user: 20 text admissions and 300 reserved voice seconds per UTC day.
- Global daily admissions: 2,000 text turns and 36,000 voice seconds.
- Maximum simultaneous reservations: 10 text, 5 voice. Text overload is rejected with a retry message. Voice overload permits text fallback.
- Guest creation: 600/IP/hour (shared Wi-Fi friendly) and 1,000 globally/day. Clearing browser storage can create a new guest; per-person enforcement for anonymous users is inherently approximate. Global caps remain authoritative. No CAPTCHA is falsely claimed.
- Voice is reserved in one block of up to 300 seconds; early client stop does not release/refund it because a bearer Google credential remains usable until server-defined expiry. Google token `expireTime` enforces the limit even if the UI timer is bypassed. Provider failure before returning a credential refunds the reservation. Up to 30 RAG tool calls per voice lease.
- Idempotent text request IDs return a previous result without charging twice. All text counters and concurrent admission checks use one transactional database lock across Edge isolates. Text reservation expires after 120 seconds if a worker dies.
- Guest transcripts are server-owned for text; bounded voice transcript uploads require that visitor's valid voice lease. Client history never establishes identity, permissions or a booking confirmation.
- Text history is bounded to 100 messages. Conversations expire after 30 days; a nightly job deletes expired beta records and cascades their requests. Retention is not a permanent archive.
- `casey_beta_settings.enabled=false` stops new admissions. Existing issued Google tokens remain bounded by their expiry. Settings are service-only; quotas measure admissions, not exact euros. Provider quota errors can still happen before our cap.

## Validation and deployment

Database verification `tools/beta/verify_database.py` runs only on isolated Preview and requires `CASEY_BETA_TEST_PROJECT=sneaxpqnmlhnrhoautjx` and a server-side service key in environment; never commit keys. It covers isolation, idempotency, quotas, bursts of 5/10/20/50, concurrent caps and failed-provider refund. This is admission-control load testing, not a claim that 50 simultaneous model/audio sessions were measured.

Node tests cover native adapter and guest transport; Deno tests cover current backend/RAG and safe auth MIME. Production release report records real text/Live/OTP verification, served bytes, commit, deployment, rollback, and physical-device gaps. Apply the three additive beta migrations before deploying beta functions. Existing workflows deploy functions on main but deliberately do not auto-apply every historical database migration.

Rollback: disable new beta admissions and restore prior frontend; keep beta tables/migrations and RAG corpus intact. Do not reverse migrations by deleting user conversations.
